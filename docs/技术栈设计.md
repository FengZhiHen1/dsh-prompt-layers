# 技术栈与兼容性

使用 Node ESM，无编译步骤；测试采用 node:test。Host Config 使用 Schemastery，YAML 使用 yaml 2.x，发布的 Draft 2020-12 Schema 使用 Ajv 8.x。客户端使用宿主 React 和 lazy module loader，不加载 Harness Client 包。

目标基线为 DSH 0.2.1-rc.2 / 687f282e，兼容已验证的上一代 0.2.0-rc.2 / 639ed015。插件只消费 Cordis 注入的服务，未导入其服务定义，不安装额外 Cordis 副本。两代契约断言的差异仅行号，接口形态与执行顺序一致。

`package.json` 声明 `engines.dsh` 为 `>=0.2.0-rc.2 <0.3.0-0`：宿主预检按 `includePrerelease` 求值，该区间覆盖两个 0.2 代预发布，排除 0.1.7 与 0.3 预发布。未声明 DSH peer 依赖，因此 `engines.dsh` 单独决定兼容判定。扩展兼容代际时同步改此区间与 `test/runtime-v1.test.mjs` 的接受列表。

关键接口由目标实例 Inspect 核对：systemPrompt.assemble、system-prompt/assemble waterfall、tools.get(name, scope)、agentPresets.composedPreset/list/acquireScope、connection.fetch.register、session/event，以及 Client plugins.bundle.config、slots 与 locale。

## 模型层的路由时序与边界

源码 `packages/core/agent-loop/src/agent.ts` 在 `prepareRequest` 前执行 `renderPrompt`；`assembleContextFor` 传入当前 `{ agent, scope: agent }`，agent-loop 注册的 `{{provider}}`/`{{model}}` 变量的默认解析器读 `agent.options.provider/model`。但该默认值只是 Agent 创建时抓取的“应用默认模型”（`dsh-api-session-controller.agentOptions()` → `agentDefaultModel.currentSelection()`），而 `dsh-agent` 的 Session 模型选择（`installModelSelection`）会在同一个 `system-prompt/assemble` waterfall 内、`next()` 之后把 `assembly.variables.provider/model` 覆写为该会话真正要用的路由。因此模型层取的是 waterfall 之后的这两个变量，只有装配未声明路由时才回退 `agent.options`。

同一处源码在组装之后才进入 `agent/request` 与 `prepareCall`；已渲染文本不会因请求级路由覆盖或 retry 重建，`agent/request` 的 CallConfig 也不允许修改 messages。插件按装配路由选择模型层，不观察该后续覆盖；这是当前边界。若未来宿主提供正式 post-route 重组接口，再重新验证晚改路由、重试、主子不同模型及压缩后恢复。

不通过私有字段、函数劫持或 user-role 补丁实现模型规则。路由来自宿主在装配结束时给出的 `provider`/`model` 变量，回退到 Agent 创建选项，不是按显示名、旧模型或默认模型快照猜测。`status.modelLayers` 的取值沿用历史名 `declared-route`，语义即“该次装配实际渲染的路由”。

## 保守能力边界

公开 assembly 不含静态/动态注册来源和 complete 标志；既有段均按受管处理，修改要求显式许可。宿主 complete 在 waterfall 后恢复为唯一段，提交观察必须区分 suppressed-or-changed，不承诺绕过。

tools.get 的 scoped 视图可证明底层 pwsh 工具对该 Agent 可见（含 PTC）；存在即判定 Agent 能执行 PowerShell，条件按此匹配。未注册该工具的第三方 shell 后端不匹配；没有增加 OS 名、显示名或其他工具名的猜测，也没有每次 Shell 探测。若某后端实际使用 PowerShell 却不暴露 `pwsh` 工具，需要该后端补齐工具身份，不能在插件里按名称推断。PowerShell 模板默认 `position: after: tool:pwsh`：模板加入草稿与 Host import 都写入该位置，条件命中时紧跟原生工具段。`validateHost` 从该次 assembly 的原生 `tool:pwsh` 推导 PowerShell 能力；缺少该工具的 preset 只按 `powershell: false` 校验，避免伪造不可满足的 `powershell: true` 锚点。

文件适配器仅支持根内受控相对路径，拒绝符号链接，限制文件数与字节数；保存采用修订检查和同目录临时文件替换。Node 的跨平台 rename 无 compare-and-swap，因此外部编辑器在最终检查到 rename 之间仍存在极小竞态窗口；不能宣称多文件事务。
